# 1. Purpose

Interrupts and exceptions form the event-handling backbone of Kernec. Every interaction between hardware, software, and the processor ultimately enters the kernel through a controlled interrupt or exception path.

This specification defines the architecture, responsibilities, ownership, and implementation rules governing interrupt handling throughout Kernec.

The objectives are:

- deterministic interrupt handling
- minimal interrupt latency
- predictable scheduling behaviour
- architectural portability
- complete fault isolation
- security across privilege boundaries

No interrupt subsystem implementation shall begin until this specification is approved.

---

# 2. Engineering Philosophy

Interrupt handling follows several immutable engineering principles.

## 2.1 Correctness Before Speed

An interrupt handler that occasionally corrupts system state is unacceptable regardless of benchmark performance.

Interrupt latency is important.

System correctness is mandatory.

---

## 2.2 Keep Interrupts Short

Interrupt handlers should perform only the minimum work required to acknowledge hardware and capture state.

Lengthy processing shall always be deferred.

---

## 2.3 Separate Hardware from Policy

Hardware-specific code belongs inside the Architecture Layer.

Scheduling, drivers and kernel services must never directly manipulate CPU interrupt hardware.

---

## 2.4 Deterministic Behaviour

Interrupt execution paths should be bounded and predictable.

Unbounded loops inside interrupt context are prohibited.

---

## 2.5 Security First

Every transition from Ring 3 into Ring 0 shall undergo complete validation.

User space must never influence privileged execution without explicit kernel verification.

---

# 4. Interrupt Classification

Kernec recognizes four categories of CPU events.

## 4.1 Exceptions

Exceptions originate from CPU execution itself.

Examples include:

- Divide-by-zero
- Invalid opcode
- Page fault
- General protection fault
- Double fault

Exceptions are synchronous.

They occur because of the currently executing instruction.

---

## 4.2 Hardware Interrupts (IRQs)

Hardware interrupts originate from external devices.

Examples:

- Keyboard
- Mouse
- Storage controller
- Network adapter
- Timer
- USB controller

IRQs are asynchronous.

They may occur regardless of the instruction currently executing.

---

## 4.3 Software Interrupts

Software interrupts are intentionally generated by software.

Typical uses include:

- legacy system calls
- debugging
- virtualization

Modern Kernec prefers dedicated syscall instructions over software interrupt instructions where hardware supports them.

---

## 4.4 Inter-Processor Interrupts (IPIs)

IPIs exist only on multiprocessor systems.

They allow one CPU core to interrupt another.

Uses include:

- scheduler rescheduling
- TLB shootdowns
- stopping processors
- synchronization
- SMP startup

---

# 5. Interrupt Descriptor Table (IDT)

Every processor core owns its own Interrupt Descriptor Table.

The IDT contains 256 entries.

| Vector Range | Purpose |
|--------------|----------|
| 0–31 | CPU Exceptions |
| 32–223 | Hardware IRQs |
| 224–239 | Inter-Processor Interrupts |
| 240–255 | Reserved for Future Expansion |

Each IDT entry shall contain:

- handler address
- privilege level
- interrupt gate type
- present flag
- selector

No user process may modify any IDT entry.

---

# 6. Exception Handling

Exceptions indicate abnormal execution.

The kernel must preserve diagnostic information before recovery or termination.

## 6.1 Fatal Exceptions

Examples:

- Double Fault
- Machine Check
- Triple Fault

These immediately trigger a kernel panic.

Recovery is prohibited.

---

## 6.2 Recoverable Exceptions

Examples:

- Page Fault
- Breakpoint
- Debug Trap

Recovery depends upon subsystem policy.

The memory manager owns page fault recovery.

The debugger owns breakpoint handling.

---

## 6.3 User Space Exceptions

If an exception originates from Ring 3:

- save processor context
- determine fault cause
- deliver appropriate signal
- terminate process if unrecoverable

The kernel itself must continue operating.

---

# 7. Interrupt Context Rules

Interrupt handlers execute under strict limitations.

The following operations are forbidden inside interrupt context:

- blocking locks
- sleeping
- waiting for I/O
- dynamic memory allocation unless explicitly marked atomic
- filesystem operations
- scheduler blocking primitives

Permitted operations include:

- acknowledging hardware
- updating atomic counters
- recording timestamps
- queuing deferred work
- waking waiting threads

Interrupt handlers shall complete as quickly as practical.

---

# 8. Deferred Work

Lengthy processing must never occur directly inside interrupt handlers.

Instead it is deferred.

Kernec supports deferred execution mechanisms including:

- Deferred Procedure Calls (DPC)
- Bottom Halves
- Kernel Worker Threads

The interrupt handler performs only:

1. acknowledge hardware
2. capture event information
3. queue deferred work
4. return

All expensive work executes later.

---

# 9. Timer Interrupt

The timer interrupt drives the scheduler.

Responsibilities include:

- decrement current thread time slice
- account CPU usage
- update kernel time
- trigger scheduler when required
- execute periodic kernel maintenance

Timer interrupt frequency shall remain configurable.

Default development frequency:

```
1000 Hz
```

One interrupt every millisecond.

---

# 10. Nested Interrupt Policy

Nested interrupts are permitted only under controlled conditions.

Higher-priority interrupts may pre-empt lower-priority handlers.

Equal or lower priority interrupts remain masked until completion.

Kernel code must always leave interrupt nesting balanced.

Interrupt enable and disable operations must never leak across subsystem boundaries.
